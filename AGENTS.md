# Repository Guidance

Micronaut Camel integrates Apache Camel 4 with Micronaut 5. It was created from micronaut-project-template. Keep root guidance short and update it when the build changes.

## Repository Shape

- `camel-core/` is the runtime integration, published as `micronaut-camel-core` (`useStandardizedProjectNames`).
- `camel-processor/` (`micronaut-camel-processor`) is the annotation processor:
  - `CamelConfigVisitor` generates code from the Camel catalog for classes annotated with `@CamelConfig`: the `@RequiresCamel*` annotations of `camel-core`, and the camel-main `@ConfigurationProperties` of `camel-configuration/`, and the component, data format and language `@ConfigurationProperties` of the extension modules (`@CamelConfig(artifacts = ...)` selects the extensions of one Camel artifact). Keep generated configuration classes out of `camel-core`: Micronaut writes the configuration metadata of one annotation processing round only, and `camel-core` has configuration readers of its own (the `/camel` endpoint). Camel applies the options at runtime through camel-main; the generated classes document them. Micronaut writes the `enum` keyword of a configuration schema only for enum-typed properties, so the visitor also writes `META-INF/micronaut-configuration-schemas/<class>.values.json` (`ValuesSchemaGenerator`): a schema of the same prefix with the possible values of the catalog and `additionalProperties: {}`, which the configuration validator of Micronaut JSON Schema combines with the schema of the class (tested in `camel-configuration`).
  - `CamelAnnotationsVisitor` handles Camel's bean annotations at compile time: `@EndpointInject`/`@Produce` become `@CamelInject`-qualified injection points served by a generated factory per class, `@Consume` methods become executable, and `@Converter` classes get a generated loader. Groovy cannot add generated sources, so there the classes are marked for Camel's runtime bean post-processor instead.
- `camel-platform-http/` (`micronaut-camel-platform-http`) is the `PlatformHttpEngine` of Camel's `platform-http` component (and so of the REST DSL) on the Micronaut HTTP server. A server filter dispatches the requests no Micronaut route matches to the started consumers. Its `jettyTest` test suite runs the engine on Jetty from micronaut-servlet.
- `camel-servlet/` (`micronaut-camel-servlet`) registers Camel's `CamelHttpTransportServlet` (the `servlet` component) with the servlet containers of Micronaut Servlet, through a `ServletContainerInitializer` bean, configured with `camel.servlet.mapping.*` (read with `@Value`, not `@ConfigurationProperties`: the module also holds the generated `servlet` component configuration, and Micronaut writes the configuration metadata of one processing round only). Its tests run on Jetty (`test`), Tomcat (`tomcatTest`) and Undertow (`undertowTest`), from the same sources; the initializer destroys the servlet itself on shutdown, as Undertow does not and Camel's servlet registry is JVM-wide.
- `camel-core/` also holds the operations integrations, in `io.micronaut.camel.health`, `.management`, `.micrometer` and `.tracing`. They use `compileOnly` dependencies on micronaut-management, micronaut-micrometer, micronaut-tracing and the Camel artifacts, and are gated with `@Requires`, so they are only active when the application adds those modules.
- `camel-core` also integrates Camel's messaging components with the Micronaut messaging modules, in the `io.micronaut.camel.kafka`, `.jms`, `.rabbitmq`, `.nats` and `.mqtt` packages: `ComponentCustomizer` and factory beans that configure a component from the module's configuration when both are on the classpath (`compileOnly` dependencies, `@Requires(classes = ...)` plus the generated `@RequiresCamel*` annotation), never overriding `camel.component.<name>.*`. Their own settings are under `micronaut.camel.<integration>.*`.
- `camel-test/` (`micronaut-camel-test`) adds Camel test annotations, such as `@MockEndpoints`, `@UseAdviceWith` and `@EnableRouteCoverage`, to `@MicronautTest` tests. `@EnableRouteCoverage` dumps the coverage from Camel's `ManagedCamelContext` (needs `camel-management`, `compileOnly` here) when the context stops, to `build/camel-route-coverage/<class>-<last test method>.xml` (`micronaut.camel.test.route-coverage.directory`), and registers a DOM-to-string converter as Camel needs camel-xml-jaxp for it.
- `camel-bom/` is the BOM. It imports `org.apache.camel:camel-bom`.
- `buildSrc/src/main/groovy/io.micronaut.build.internal.camel-*.gradle` holds the convention plugins (and `buildSrc/src/main/groovy/io/micronaut/build/camel/` their task classes, un-ignored in `.gitignore`): `camel-base`, `camel-module` for published modules, and `camel-tests` for the test suites.
- `test-suite`, `test-suite-kotlin` (KSP) and `test-suite-groovy` (Spock) hold the guide samples. Every sample is a `snippet::` with the same fully qualified name, under `io.micronaut.camel.docs`, in each suite. The suites have the Netty server, so every `@MicronautTest` starts a server.
- Every sample suite runs the JSON schema samples (`io.micronaut.camel.docs.jsonschema`) in a `jsonSchemaTest` suite of its own (part of `check`), from the same sources, excluded from `test`: they use `camel-json-validator` (NetworkNT JSON Schema 2, Jackson 2), which breaks with the `micronaut-json-schema-validation` (NetworkNT 3, Jackson 3) that micronaut-mcp brings to `test`. KSP ignores the filters of source sets (and takes the Kotlin directories as Java source roots too), so the KSP tasks of `test-suite-kotlin` process a filtered copy of `src/test/kotlin` (`kspTestSources`, `kspJsonSchemaTestSources`).
- `test-suite-python` holds the Python (Pyronaut) versions of the samples, under `micronaut.camel.docs` (the macro drops the leading `io.`). It runs with `./gradlew :test-suite-python:test -Ppython-ci` on GraalVM. New samples get a Python version too (routes extend `RouteBuilder` and call `self.from_(...)`; Java methods named like Python keywords take a trailing underscore, such as `in_`). A snippet without a version in some language lists its languages, such as `languages="java,python"`. Python classes do not keep Micronaut or Camel annotations on the generated Java class, so read annotations from the bean definition's annotation metadata, not by reflection (as `CamelConsumeMethods` does for `@Consume`).
- `CamelAnnotationsVisitor` handles Python classes like Java ones: the attributes of a Python class are bean properties (injected through setters), so the visitor annotates the properties, and it writes its generated code as Java sources.
- Python tests cannot implement `TestPropertyProvider` (Micronaut Test calls it before the GraalPy runtime exists): the services of the Python samples (Kafka, Redis, a free server port) are provided by `io.micronaut.camel.testservices.DocsServices` (`src/test/java`, an `ApplicationContextConfigurer`) for the `docs-*` environment a test selects. Its property sources are added once the bean configurations are enabled, so a module whose package requires a property (Micronaut Redis: `redis`) gets it from `application-docs-<env>.yml` with a placeholder. The suite runs the `io` and `blocking` executors on platform threads: GraalPy does not run Python code on virtual threads.
- `test-suite/src/test/java/io/micronaut/camel/examples/<name>` ports a camel-spring-boot-examples example: its beans are `@Requires(env = "example-<name>")`, its test is `@MicronautTest(environments = "example-<name>")` and its configuration is `application-example-<name>.yml`.
- `test-suite-graal` runs Camel in a native image with `./gradlew :test-suite-graal:nativeTest` (GraalVM 25). The `CamelNativeFeature` of `camel-core` registers the classes of Camel's service files and the classes the processor lists under `META-INF/micronaut-camel/native`; keep new reflective or service-file-based features covered there.
- `camel-core` has the `cli` package: a `CliConnectorFactory` bean for `camel-cli-connector` (Camel JBang's CLI) whose connector closes the Micronaut application context on `camel stop`; `camel.cli.enabled=false` disables the connector, which Camel otherwise enables from the classpath. Cluster services (`camel.cluster.*` or `CamelClusterService` beans), the supervising route controller (`camel.routecontroller.*`) and the debugger (`camel.debug.*`) need no code: camel-main applies them, and `camel-core` tests cover them.
- `camel-core` bridges `hazelcast` (the `HazelcastInstance` of micronaut-cache-hazelcast), `ehcache` (the Ehcache `CacheManager` and `ehcache.caches.*` of micronaut-cache-ehcache) and `gcp` (the project of micronaut-gcp: the `projectId` component option of the Google components, and the `{{gcp.project-id}}` placeholder through a `PropertiesSource` bean); Pulsar's `pulsarClient`, MongoDB's `mongoConnection` (micronaut-mongo-sync), OpenSearch's `client`/`openSearchClient` (prototype beans of micronaut-opensearch-restclient) and the Jackson 3 mapper of micronaut-jackson-databind for camel-jackson3 (only with `autoDiscoverObjectMapper`) are autowired by Camel, tested without code of ours. Their tests, and those of the CLI connector, are in the `ecosystemTest` and `cliTest` test suites of `camel-core`, which keep those dependencies off the main test classpath (`cliTest` runs with its own `user.home`, where the connector writes its files).
- `test-suite-graal` runs Camel in a native image with `./gradlew :test-suite-graal:nativeTest` (GraalVM 25): core, YAML, bean binding, annotations, platform-http, Micronaut Serialization JSON and type conversion, camel-jackson, camel-sql (and `JdbcAggregationRepository`) on H2 with micronaut-jdbc-hikari, camel-kafka, and the `jsonschema:` resources and type validators with the Micronaut JSON Schema validator (the schemas under `META-INF/schemas` are resources of the image, by the reachability metadata of `camel-core`). The `CamelNativeFeature` of `camel-core` registers the classes of Camel's service files, the classes the processor lists under `META-INF/micronaut-camel/native`, the data source getters Camel's service location reads, `DefaultExchangeHolder` with common JDK types for serialization, and a list of the route resources (`META-INF/micronaut-camel/native-resources`, read by `NativePackageScanResourceResolver`, as images with runtime class loading cannot list resources); keep new reflective or service-file-based features covered there, generically. Everything is initialized at runtime (no build-time init), so runtime class loading (Crema) stays possible: `-Pcrema` builds the test image with `-H:+RuntimeClassLoading`, and the whole suite passes with it.
- `test-suite-graal` applies the `io.micronaut.minimal.library` and `io.micronaut.test-resources` plugins (from `micronaut-test-resources-plugin` on the `buildSrc` classpath): the test resources server provides `kafka.bootstrap.servers` to the JVM and native tests, and `NativeKafkaTest` is skipped (`@EnabledIf`) when the server cannot resolve it, for example without a container runtime. Tests needing a service use their own environment (`application-<env>.yml`) and `@Requires(env = ...)` beans.
- `camel-aot/` (`micronaut-camel-aot`) is a Micronaut AOT optimization (`camel.service.index`) that indexes Camel's service files and type converter loader lists as generated code, loaded as a `CamelServiceIndex` static optimization; `CamelContextFactory` then creates an `IndexedCamelContext` (`io.micronaut.camel.optimizations`), which falls back to the classpath for files that are not indexed. `camel-aot` is not a Camel catalog artifact, so it is a plain module.
- Exchange persistence with the Micronaut JSON mapper: `JsonExchangeCodec` (`json` package, stores body, headers and aggregation properties with type names; reads only JDK value types, collections and introspected types), used by `JsonJdbcCamelCodec` (`jdbc`, camel-sql's `JdbcAggregationRepository`), `JsonLevelDBSerializer` (`leveldb`) and `MicronautCacheAggregationRepository` (`cache`). `JsonTypeConverter` is a fallback converter between `@Serdeable` types and JSON strings/bytes/streams and maps (`micronaut.camel.json.type-converter.enabled`); `ConversionServiceTypeConverter` already converts maps to beans.
- `camel-core` integrates other Micronaut modules in sub-packages, behind `@Requires(classes = ...)` with `compileOnly` dependencies: `transaction` runs `transacted()` routes in Micronaut Data transactions (`MicronautTransactionPolicy`, named `PROPAGATION_*` policy beans, a transactional error handler), and `jdbc` gives Camel a `DataSource` that joins the current Micronaut transaction and works outside one. Registry beans are adapted for Camel by `CamelBeanAdapter` beans.
- The test suites' `application.yml` configures an H2 data source with `transaction-manager: springJdbc` (micronaut-data-spring-jdbc) for the transaction samples. Examples needing PostgreSQL or Kafka start them with Testcontainers and are skipped without a container runtime.
- The sample suites have Micronaut Security on the classpath but disabled (`micronaut.security.enabled: false` in `application.yml`); the tests that need it use their own environment (`docs-security`, likewise `docs-mcp` for the MCP server). Likewise micronaut-cache-infinispan is disabled (`infinispan.enabled: false`) except in the infinispan example. Every guide sample route loads in every test of its suite, including the example tests: the REST DSL samples bind JSON, so example REST services that do not bind set `bindingMode: off`.
- Tests that need a service (Redis, LocalStack, Azurite, Vault, PostgreSQL, Qdrant, Infinispan, ArangoDB, HAPI FHIR) start it with Testcontainers in a `TestPropertyProvider` and stop it in `@AfterAll`. HTTP services that are public APIs or too heavy for a container (docling-serve) are `@Controller`s of the example's environment, with the server on a `SocketUtils` port that the `TestPropertyProvider` sets. Under Podman, run them with `TESTCONTAINERS_RYUK_DISABLED=true`; containers whose Testcontainers module mounts the Docker socket (LocalStack) run as generic containers.
- `camel-core`'s `executor` package has `MicronautThreadPoolFactory`, a Camel `ThreadPoolFactory` bean (camel-main picks up a single one from the registry) enabled with `micronaut.camel.executors.enabled`: non-scheduled Camel thread pools become `ExecutorServiceView`s on a Micronaut executor bean (`default-executor`, `blocking` by default; `profiles.<profile id>` per thread pool profile; `camel` keeps Camel's pools), which keep the profile's pool size, queue and rejected policy and whose shutdown never stops the Micronaut executor. Scheduled pools stay Camel's. Thread pool profiles are configured with `camel.threadpool.config.<id>.*` or `ThreadPoolProfile` beans.
- XML routes are rejected: `MicronautCamelMain.modelineRoutes` (where Camel first reads the route resources) and `MicronautRoutesCollector` fail with a clear message when `camel.main.routes-include-pattern` matches `.xml` files and no XML `RoutesBuilderLoader` is present.
- `test-suite` has an `openapiTest` suite (part of `check`) with the micronaut-openapi annotation processor, kept off the main test sources: the Swagger UI view (`swagger-ui.spec.url`) shows Camel's REST DSL OpenAPI document.
- `.agents/skills/` is shared agent guidance synced from the template.

## Scope

- Routes are written in the Java DSL (including the Endpoint DSL) or the YAML DSL. XML routes and Spring XML contexts are not supported (and rejected at startup). Kotlin and Python use the Java DSL: Java DSL methods named like keywords need backticks in Kotlin (`` `when` ``, `` `in` ``) and a trailing underscore in Python (`from_`, `in_`).
- Camel components are configured through Micronaut configuration (`camel.component.<name>.*`).
- `MicronautPropertiesSource` rewrites the map-typed camel-main options (`VALUE_MAP_OPTIONS`, `OBJECT_MAP_OPTIONS`, such as `camel.rest.api-properties` and `camel.threadpool.config`) to Camel's `option[key]` syntax, reading each as a sub-map with raw keys. `MapOptionsTest` fails when camel-main gains a map option missing from those sets.
- Every Camel artifact with components, data formats or languages has a module, `micronaut-camel-<x>` for `camel-<x>`, with no directory in the repository. The `io.micronaut.build.internal.camel-extensions` settings plugin (`settings-build-logic/`) includes one project per artifact of the Camel catalog, with its directory under `target/camel-extensions/`, and applies the `io.micronaut.build.internal.camel-extension` convention plugin of `buildSrc` to it. That plugin writes a `@CamelConfig(artifacts = "camel-<x>")` class into the generated sources, in `io.micronaut.camel.components.<x>`, and adds the `api` dependencies on `micronaut-camel-core` and the Camel artifact. A real project named after a Camel artifact, such as `camel-platform-http`, is that artifact's module and gets the same configuration. The `generateCamelExtensionsReference` task of the root project writes the module table of the guide. Exclusions (extensions needing Spring Boot) are listed in the settings plugin.
- All modules, the extension modules included, are released to Maven Central in the single bundle of micronaut-build's `prepareBundle`/`publishToMavenCentral`. The extension modules build their javadoc with `--no-fonts`, which keeps the bundle small.

## Versions

- Micronaut core is 5.2.x, micronaut-micrometer 6.1.x and micronaut-tracing 8.3.x (catalogs `mnMicrometer` and `mnTracing`); the other module catalogs (`mnSecurity`, `mnRedis`, `mnValidation`, `mnObjectStorage`, `mnMcp`, `mnLangchain4j`, `mnAws`, `mnAzure`, `mnSql`, `mnGcp`, `mnPulsar`, `mnMongo`, `mnOpensearch`, `mnOpenapi`, `mnJsonSchema`) follow the versions of Micronaut Platform 5.2, and Camel is 4.22.x (`managed-camel` in `gradle/libs.versions.toml`). The generated code follows the Camel catalog of that version, so upgrading Camel regenerates it.

## Code

- Integrations with other Micronaut modules live in `camel-core` sub-packages (`event`, `scheduling`, `executor`, `cache`, `json`, `vault`, `security`, `redis`, `objectstorage`, `httpclient`, `mcp`, `cli`, `hazelcast`, `ehcache`, `gcp`...) behind `@Requires`, with `compileOnly` dependencies: no module per integration. Components of `camel-core` (`micronaut-event`, `object-storage`, `micronaut-http`) are `@Named` beans that the registry bridge finds by scheme. The MCP integration plugs into camel-main's `camel.server.mcp-*` options with a `McpServerFactory` bean, so it needs only `camel-mcp-server-api`.

- `camel-core`'s `jsonschema` package uses the schemas that Micronaut JSON Schema generates for `@JsonSchema` types (found among the bean introspections, never by scanning): the `jsonschema:` Camel resources (a `resource-loader-jsonschema` `ResourceResolver` bean), a Camel `Validator` per type for `inputTypeWithValidate`/`outputTypeWithValidate` (backed by Micronaut's `JsonSchemaValidator`, or by a `json-validator` endpoint without it), and a `RestApiProcessorFactory` that replaces the REST DSL's camel-openapi-java component schemas with the generated ones (tested in `camel-platform-http`). Disabled with `micronaut.camel.json-schema.enabled` / `micronaut.camel.json-schema.openapi.enabled`.

- JSpecify `@NullMarked` goes only on `package-info.java`; every package has one. Use `org.jspecify.annotations.Nullable` for nullable types.

## Documentation

- User guide sources live in `src/main/docs/guide`, with navigation in `toc.yml`.
- Build the guide with `./gradlew publishGuide`.

## Verification

- `./gradlew check` runs the tests. The messaging tests start brokers with Testcontainers (in `TestPropertyProvider` tests); with Podman, Ryuk may fail to mount the socket, so run them with `TESTCONTAINERS_RYUK_DISABLED=true`. The tests stop their containers themselves.
- `./gradlew check` runs the tests. With Podman, run it with `TESTCONTAINERS_RYUK_DISABLED=true`, as Ryuk cannot mount the Podman socket.
- Run `./gradlew publishGuide` after guide or `toc.yml` changes.
