Camel reads its configuration from the Micronaut environment, so Camel options can be set in any Micronaut property source: `application.yml`, environment variables, system properties or a distributed configuration source. The property names are those of https://camel.apache.org/components/next/others/main.html[Camel Main] and of the Camel components:

[configuration]
----
camel:
  main:
    name: shop
    shutdown-timeout: 30
  component:
    seda:
      queue-size: 500
----

* `camel.main.*` configures the `CamelContext`, for example its name, the routes to load, stream caching and tracing.
* `camel.component.<name>.*`, `camel.dataformat.<name>.*` and `camel.language.<name>.*` set options of a Camel component, data format or language.
* Camel's other configuration groups, such as `camel.rest.*`, `camel.health.*`, `camel.ssl.*` and `camel.vault.*`, are also available.

Camel logs a summary of the options it applied when the application starts.

=== Map options

Some Camel options are maps, such as the thread pool profiles of `camel.threadpool.config`, the REST options of `camel.rest.api-properties` and `camel.rest.cors-headers`, and `camel.main.global-options`. They are set as nested configuration, and the keys are kept as written, dots included:

[configuration]
----
camel:
  threadpool:
    config:
      bulk:
        pool-size: 20
        max-pool-size: 50
  rest:
    api-properties:
      api.title: Orders
      api.version: 1.0.0
    cors-headers:
      Access-Control-Max-Age: 3600
----

Camel's own `camel.rest.cors-headers[Access-Control-Max-Age]` syntax also works in property files.

=== Several instances of a component

`camel.component.<name>.*` configures the component of that name. To use the same component with two configurations, for example two Kafka clusters, declare a second instance with camel-main's `camel.beans.*` options: the bean name becomes the scheme of its endpoints.

[configuration]
----
camel:
  component:
    kafka:
      brokers: orders.example.com:9092
  beans:
    audit: "#class:org.apache.camel.component.kafka.KafkaComponent"
    audit.brokers: audit.example.com:9092
----

Routes then use `kafka:orders` for the first cluster and `audit:events` for the second. camel-main normalizes the names of these beans, so use letters and digits only.

=== Unknown options

Camel Main applies the `+camel.component.*+`, `+camel.dataformat.*+` and `+camel.language.*+` options when the `CamelContext` is created, and by default it fails the startup of the application when an option cannot be applied, for example an option that the version of the component on the classpath does not have, as when the configuration was written for a newer Camel version than the application's:

[configuration]
----
camel:
  component:
    seda:
      queue-size: 500
      option-of-a-newer-camel: true
----

The application fails to start with an error that names the option. To start it anyway, turn off Camel's fail fast:

[configuration]
----
camel:
  main:
    auto-configuration-fail-fast: false
----

Camel then applies the options it knows and ignores the others, without a warning: the options that Camel applied are listed in the auto-configuration summary that it logs at startup, so an ignored option is the one missing from the summary. Micronaut Camel keeps Camel's default, as an option that is silently ignored is harder to diagnose than a failed startup.

The options of a component that is not on the classpath fail the startup in both cases, as Camel cannot create the component to configure it.

NOTE: The options documented by the <<modules, Camel modules>> are those of the Camel version of Micronaut Camel, which is the version of the Camel BOM it imports. An application that upgrades or downgrades Camel itself may find options of the reference that its components do not have.

=== Validating the configuration at build time

Camel finds unknown options when the application starts. The https://micronaut-projects.github.io/micronaut-json-schema/latest/guide/#configurationValidator[configuration validator of Micronaut JSON Schema] finds them earlier, in a build or a CI pipeline, without starting the application, with the configuration schemas that the jars of Micronaut modules have:

dependency:io.micronaut.jsonschema:micronaut-json-schema-configuration-validator[]

Each <<modules, Camel module>> has the schemas of the options of its components, data formats and languages, such as `+camel.component.seda.*+` for `micronaut-camel-seda`, and `micronaut-camel-configuration` has those of `+camel.main.*+` and of the other configuration groups of Camel. The schemas give the type of each option, and the possible values of the options that the Camel catalog lists them for. With this configuration:

[configuration]
----
camel:
  main:
    shutdown-timout: 5
    jmx-management-statistics-level: All
  component:
    seda:
      queue-sise: 500
      concurrent-consumers: two
----

the validator reports:

[source]
----
camel.main.shutdown-timout: Property not present in schema. Did you mean: camel.main.shutdown-timeout, ...?
camel.main.jmx-management-statistics-level: Value not in enum. Expected one of: 'Extended', 'Default', 'RoutesOnly', 'Off'
camel.component.seda.queue-sise: Property not present in schema. Did you mean: camel.component.seda.queue-size?
camel.component.seda.concurrent-consumers: Expected integer
----

Run the validator from the command line of a build, with the runtime classpath of the application:

[source,bash]
----
java -cp <runtime-classpath> io.micronaut.jsonschema.configuration.validator.cli.ConfigurationJsonSchemaValidatorCli \
  --classpath <runtime-classpath> \
  --environments prod \
  --out build/reports/configuration
----

or with its API, for example in a test, where `ConfigurationJsonSchemaValidator` validates an `Environment`. The module also has a `ConfigurationErrors` bean and, with Micronaut Management, a health indicator that is `DOWN` when the configuration has errors.

The validator only knows the options of the components whose module is on the classpath: the options of a component that has only its Camel artifact, such as `org.apache.camel:camel-seda` instead of `micronaut-camel-seda`, are not validated, and neither are those of components that are not on the classpath, which Camel itself fails on at startup.

=== IDE support and the configuration reference

The `micronaut-camel-configuration` module documents the `camel.main.*` options and Camel's other configuration groups as `@ConfigurationProperties`, so IDEs complete them and they appear in the configuration reference:

dependency:io.micronaut.camel:micronaut-camel-configuration[]

The classes are generated from the Camel catalog at build time. Camel itself still applies the options, so the module is optional: the options work without it. The options of each component, data format and language are documented by its <<modules, Camel module>>.

=== Requiring a Camel component

For every Camel component, data format and language, `micronaut-camel-core` has a requirement annotation in the `io.micronaut.camel.requires` package, such as `@RequiresCamelKafka`, `@RequiresCamelJacksonDataFormat` or `@RequiresCamelJsonpathLanguage`.
